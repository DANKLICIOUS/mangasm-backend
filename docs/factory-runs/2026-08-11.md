## Evidence Notes (sourced 2026-08-11)

- **A (VerifyCall Local):** decisive counter-signal, the most important
  finding of the run. Switching the trust-verification pain from text to an
  automated voice call does not sidestep 2026-08-06's scam-pattern problem —
  it walks into a worse-documented one. Vishing (voice phishing) is called
  out as **the fastest-growing scam category of 2026**, featuring AI-cloned
  voices and fake caller ID; multiple state licensing boards (Virginia
  DPOR, North Carolina DOJ) have issued live 2026 consumer alerts about
  **scam calls specifically impersonating licensing-board verification**
  ([dpor.virginia.gov](https://www.dpor.virginia.gov/Fraud),
  [ncdoj.gov](https://ncdoj.gov/consumer-alert-watch-out-for-scam-calls-targeting-professional-licensees/),
  [cybrvault.com](https://cybrvault.com/blog/ai-voice-scams-2026-deepfake-phone-calls)).
  This generalizes 2026-08-06's finding: the local-business trust-
  verification pain isn't broken because of SMS specifically — it's broken
  for **any unsolicited automated outreach channel** used to establish
  trust, voice included. `fatal_risk` marked true again.
- **B (DispatchSmart):** no evidence found to support the core premise.
  Search turned up SMSDispatch's own response-rate case study again (71% to
  87%, same source as 2026-08-04) but nothing breaking down response rates
  by driver segment or showing a personalization lift over flat SMS. It did
  surface a real competitive counter-signal, consistent with SMSDispatch's
  original counterargument: 2026-era dispatch apps are trending toward
  integrated in-app messaging with audit trails as the default, which could
  absorb a standalone channel-personalization layer as a bundled feature
  ([hakunamatatatech.com](https://www.hakunamatatatech.com/our-resources/blog/driver-app)).
  Unlike SmartRemind's clear sourced lift, this is added complexity with no
  demonstrated benefit — a meaningfully weaker case.
- **C (TrainSmart Local):** no fresh search this run. This is now the
  **4th consecutive test** of local-business compliance training (07-29
  microlearning, 08-04 community events, 08-11 personalized recs) to land
  in the same weak range with no pricing precedent ever sourced for any
  delivery mechanism in this specific pair. The pattern itself is the
  finding: the problem isn't the delivery mechanism, it's the pair.
- **D (PetMatch Safe):** no fresh search this run, but a real qualitative
  distinction from candidate A worth noting: this is a recommendation/
  trust-scoring tool the buyer proactively consults, not unsolicited
  outbound contact — structurally different from the scam-adjacent pattern
  that killed A and 2026-08-06's VerifyText Local. That difference doesn't
  fix the buyer problem, though: same unresolved question as PetCare Bites
  (2026-08-10) — no institutional payer identified, only a speculative
  B2B2C path through pet marketplaces. `buyer_clear` marked false.

## Winner — DispatchSmart · verdict: VALIDATE (composite 5.45, gate NOT passed)

**Concept:** AI-personalized channel/timing recommendations layered onto
SMSDispatch's dispatch flow. Nominal top scorer, but this is the weakest
"winner" of any run to date — not because of a strong counter-signal like
candidate A, but because there's simply no evidence the personalization
premise holds for this pair, unlike 2026-08-10's SmartRemind where the lift
was directly sourced. Read as unproven, not disproven; not worth building
speculatively when SMSDispatch's own flat-SMS MVP hasn't been validated
with a real customer yet either.

**The real finding today is candidate A, not the nominal winner.** The
local-business trust-verification pain (safe connection) has now failed
**twice**, via **two different delivery mechanisms** (SMS on 2026-08-06,
voice today), for the **same underlying reason**: any automated outreach
channel used to establish trust collides with an active, well-documented
scam pattern in that exact channel. This pain should be retired from
further primary-market testing in this pool — the problem isn't the
delivery mechanism, it's that automation itself is the wrong tool for a
trust-establishment product. A real version of this would need institutional
backing (e.g. actual licensing-board integration) that's out of scope for
this factory.
